# Docker runtime acceptance

The production Docker runtime has an optional acceptance test in `tests/test_docker_runtime.py`. It uses an **already available immutable image** and an existing environment manifest produced for that image. It does not build an image, install Docker, pull an image, or make model calls.

The container acceptance checks were **not executed in this development environment because a Docker daemon was unavailable**. The POSIX shell syntax check for `runtime/run-lean` runs independently. A skipped container test is not evidence that production isolation works.

## Enable the checks

From the package directory, point the opt-in variable to an existing Docker environment manifest:

```sh
LEAN_COMPRESSION_DOCKER_ENV=/absolute/path/to/environment.docker.json \
PYTHONPATH=src python3 -m unittest discover -s tests -p test_docker_runtime.py -v
```

The manifest must have `runtime_backend: "docker"`, an immutable `docker_image` containing a complete SHA-256 image ID or repository digest, and the runtime environment fields consumed by the runner. Its image must already be present in the selected Docker daemon; the daemon and image checks use the runner's Docker client environment. The test skips when the variable is unset, the manifest is absent, Docker is absent, the daemon is unavailable, or the referenced image is absent. An explicitly supplied malformed manifest fails instead of silently passing. No image is built or fetched to satisfy missing prerequisites.

## What is exercised

The test calls the actual `runner.execute_engine()` Docker path. A small trusted test wrapper, mounted from a world-readable temporary directory under a non-default file name, collects observations inside that same container and invokes a byte-for-byte copy of the production Lean evaluator. The request imports only `Init`, proves `True` with `True.intro`, permits no axioms, and requires successful independent kernel replay. This instruments the harness; it does not relax candidate proof restrictions or change production code.

The checks inspect behavior and kernel state rather than comparing Docker command arguments:

- Only the loopback network interface is present, no default IPv4 route exists, and a local UDP route lookup to a documentation-only address fails. The probe sends no datagram and does not contact an external service.
- The root mount is actually read-only. Attempts to create files in the compiled package and mounted evaluator directory fail, while the job directory remains writable.
- Active cgroup CPU and memory controller files report the requested **0.5 CPU** and **1,024 MiB** limits. Both cgroup v2 and conventional Docker cgroup v1 controller paths are supported. On v2, swap is disabled. PID limits, effective capabilities, `NoNewPrivs` and the in-container CPU-time limit are also inspected.
- Compiled `.olean` files exist, while no `.lean` sources or `.git` entries remain under `/opt/eval/package`, including dependency checkouts. The scan follows directory links with cycle detection. This exclusion scope is the benchmark package and its Mathlib/dependency sources; the trusted mounted evaluator and the installed Lean toolchain are intentionally outside it.

`tests/test_runner_remaining.py` adds two container checks behind the same variable. A trusted probe finds every writable mount in the container memory-backed (tmpfs, proc, devpts or mqueue) and the request read-only; the 64 MiB it writes to `/job` never reach the host's scratch directory, and a 20 MiB result comes back whole on stdout. An extraction stopped by a lowered file-size limit (exit 153) is the final `extractor_resource_limit`.

The evaluator run has a 120-second acceptance-test wall limit, allowing for the additional trusted probe wrapper. These checks read active cgroup limits; they do not deliberately trigger an out-of-memory kill or benchmark CPU throughput. Passing this test establishes the observed behavior for the selected image, Docker daemon and host at that run. Retain the manifest and immutable image identity with any production validation report.

The separate shell check invokes `sh -n runtime/run-lean`; it checks syntax only and makes no claim about Docker execution or resource enforcement.

## Mounts, permissions and the Docker client

Each attempt gets a private `0700` scratch directory on the host, holding the request and the Docker client's logs. No host directory is writable from the container: `/job` is a 320 MiB tmpfs, and only the request is bind-mounted into it, read-only, at `/job/request.json`. The container keeps the image user, root with every capability dropped. No `--user` mapping is used because the container uid relates differently to the host user on each platform:

- **Rootful Linux Docker run by a non-root user.** Capability-less root, like remapped ids under userns-remap, gets only the "other" permission bits on host-owned files, so the request is `0644`. Nothing the container writes reaches the host, so it leaves nothing there that only root could delete. `run-lean` sets `umask 022`, so the files Lean and `run-lean` create in the tmpfs stay readable by their capability-less owner.
- **Rootless Docker or Podman.** Container root is the invoking user. A `--user` mapping would turn it into a subordinate uid without access; the world-readable request is harmless.
- **Docker Desktop.** File sharing maps ownership to the host user. Scratch directories come from the harness's temporary directory (`TMPDIR`), which must be a shared path; Docker Desktop shares `/var/folders` and `/tmp` by default.

The engine's directory is mounted read-only at `/engine`, and the container runs the file passed as `--engine`, whose hash the records carry. On rootful Linux that directory and file must be world-readable, as in a normal checkout.

Lean writes its result to `/job/result.json` in the tmpfs. Once Lean exits, `run-lean`, as container init, stops anything Lean left running and returns the result and the memory evidence on stdout, after whatever Lean printed: the bytes of each readable regular file, then one trailer line of `lean-compression-output v1` and their sizes, `-` for an absent file and `!` for anything else: a link, FIFO or directory, which it never opens, or a file it cannot read. It returns at most the 256 MiB file-size limit plus one byte of the result, and its evidence copies hold at most 64 KiB plus one byte. The runner takes only a trailer that ends the client's stdout, so nothing Lean printed can pose as one, keeps what precedes the returned files as the record's `stdout`, and reads a returned file only within its cap: a larger result is unusable and larger evidence null. Output without that trailer, as from an image built before this channel, returns nothing, so the attempt is an `infrastructure_error` checker incident whose error says so; rebuild such an image.

Every Docker client call in the runner (`docker run` and the forced removal) uses `runner.docker_cli_env()`, and preflights should use it too. It passes `PATH`, `HOME`, `XDG_RUNTIME_DIR`, `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`, `DOCKER_CERT_PATH`, `DOCKER_TLS`, `DOCKER_TLS_VERIFY` and `DOCKER_API_VERSION`, plus `SSH_AUTH_SOCK` when `DOCKER_HOST` is an `ssh://` URL. API keys are not passed, and no host variable reaches the container.

After a timeout or a non-zero exit the runner force-removes the container. Only a zero exit from `docker rm -f`, or a "no such container" error (how older clients and Podman report a container that is already gone), confirms removal. If removal fails, exits with any other error, or does not finish within 10 seconds, the attempt is recorded as `infrastructure_error` with `failure_reason: container_cleanup_unconfirmed`, never as a model outcome. The container may still be running, so its scratch directory is kept instead of being deleted under it, and the worker keeps its task or slot claimed with `<name>.retained` until an operator confirms the container is gone (README, "Parallel workers").

Otherwise the host deletes the scratch directory once the container is gone. Cleanup never raises and never changes the attempt's outcome. Whatever it cannot delete stays; a container writes nothing there, but the development sandbox's Lean writes into its own scratch directory. The record gives the kept path as `resources.scratch_retained` and the cause as `resources.scratch_retained_reason`: `container_cleanup_unconfirmed` or the deletion error. Delete it once the container is gone.

The Docker client runs in its own session, so Ctrl-C reaches only the harness. An interrupted or otherwise aborted attempt kills the client, force-removes the container under the same 10-second rule and only then deletes the scratch directory; if removal is unconfirmed, the directory and the claim are kept. The interruption then propagates, with notes naming the kept directory and any `<name>.retained` written.

An in-container CPU-time limit of `ceil(wall limit × max(1, CPU quota)) + 1` seconds stops a CPU-bound container that outlives its removal; under the CPU quota it cannot bind before the wall limit. Docker policies therefore need a positive `cpu_quota`, because zero would lift the CPU limit.

`verify-references` and `baseline` run Lean in Docker unless `validation.isolation` names another backend. They then require an environment record collected in the image (`runtime_backend: docker`) whose `docker_image` equals `validation.docker_image`, and refuse any other record before writing to the output directory, as `freeze` does for container runs. The image must be a content digest: `sha256:` and 64 lowercase hex digits, optionally after `name@` as a repository digest. A tag such as `sha256:latest`, an empty or truncated ID such as `sha256:5d0da3dc9764` and a malformed reference such as `name@sha256:x` are not. `freeze` refuses a missing or other `validation.docker_image` before writing the run, `verify-references` and `baseline` before writing to their output directory, the runner before starting a container, and `runtime/prepare_image.py` refuses any other image, built or passed as `--image-id`, before running it.

`tests/test_docker_command.py` checks the exact command, mount permissions, client environment, timeout classification and cleanup handling without a daemon. Run this acceptance test on rootful Linux as a non-root user before production. Docker Desktop and rootless runtimes would not reveal a regression in the permission model.

## Memory evidence

After Lean exits, and after `run-lean` as container init has stopped anything Lean left running, it removes whatever the evaluated code may have left at `/job/peak_memory_bytes` and `/job/memory_stat` (`rm -f`, so a directory there stays), copies the container's cgroup files there and returns them with the result; a file it cannot read is skipped. The runner reads nothing returned after a timeout, which kills `run-lean` before it returns anything, or when it could not confirm the container's removal (`container_cleanup_unconfirmed`), since the container may then still be running and whatever ends the stream may have been printed by the evaluated code: those records have `peak_memory_reason: not_read_after_timeout_or_unconfirmed_cleanup` and no `memory_stat_at_exit`. Only Docker records fill these fields:

- `peak_memory_mib` comes from `memory.peak` (cgroup v2) or `memory.max_usage_in_bytes` (v1). `peak_memory_scope` labels it as the cgroup high-water mark of all memory charged to the container, page cache included; it is not a process RSS. Page cache is charged to the cgroup whose process brought a page into memory, so the `.olean` files a Mathlib import maps count toward the peak when this container is the first to read them, and hardly at all when an earlier container or the host already cached them. The peak therefore depends on cache state and evaluation order, not only on the proof.
- `memory_stat_at_exit` holds four `memory.stat` values read after Lean exited, under their cgroup v2 names: `anon`, `file` and `file_mapped` in bytes (v1: `rss`, `cache` and `mapped_file`) and the cumulative major-fault count `pgmajfault`. `file` is the page cache, tmpfs included, that the container still has charged. With `pgmajfault`, which counts faults that had to read from storage, it shows whether a high peak reflects a cold cache. Lean's anonymous memory and file mappings are released when it exits, so `anon` and `file_mapped` cover only what is still charged then, mostly `run-lean` itself; they say nothing about Lean's working set. Neither cgroup version keeps a high-water mark of anonymous memory alone. One would need sampling during the run, which `run-lean` does not do.

Memory evidence never decides an outcome. A missing, unreadable or non-regular file, a file over 64 KiB, and a value other than 1 to 20 ASCII digits (surrounding whitespace aside) leave their values null; without a peak, the record keeps `peak_memory_reason: not_instrumented` and has no `peak_memory_scope`. The macOS development profile records no memory evidence.

Images built with an older `run-lean`, including the image pinned in `configs/environment.docker.json` before the stdout channel and the local `lce-runtime:warm` and `lce-runtime:followup` images, return nothing on stdout, so this runner records every attempt in them as an `infrastructure_error` incident. The environment record does not identify the script. Inspect the image's copy, for example with `docker run --rm --network none --read-only <image> cat /opt/eval/run-lean`: this `run-lean` prints the `lean-compression-output v1` trailer.

`tests/test_runtime_gates.py` runs `run-lean` itself under the local `sh` and, where present, `dash` (Ubuntu's `/bin/sh`). It moves `/opt/eval`, `/sys/fs/cgroup` and `/job` into a temporary directory holding fake cgroup v1 and v2 files and a stand-in for Lean, then checks what the runner records from what `run-lean` returns, including oversized files and values, and that it reads nothing returned before a timeout. It observes no real cgroup. `tests/test_runner_remaining.py` checks the returned files and trailer the same way, under each shell, including links, FIFOs, directories and unreadable files.

## Host disk use

No host directory is writable from the container. The image filesystem is read-only (`--read-only`), `/engine` and the request are read-only bind mounts, and every writable mount is memory: the 320 MiB `/job` and 128 MiB `/tmp` tmpfs mounts, and Docker's own `/dev` and `/dev/shm` (64 MiB each), `/dev/pts`, `/dev/mqueue` and `/proc`. What candidate code writes there counts against the container's memory limit and vanishes with the container. `--ulimit fsize=268435456` stops each file at 256 MiB, less than `/job` holds, so a result too large stops Lean with SIGXFSZ, a resource limit, before `/job` fills.

On the host an attempt writes its request and the Docker client's `stdout.log` and `stderr.log`. The client writes them under the harness's 256 MiB per-file limit, and everything the container returns passes through `stdout.log`, so Lean's output and the returned files share that limit. The client ignores SIGXFSZ: it reports the failed write and exits 1, leaving the log at the limit, and the runner records such an attempt as `verification_resource_limit` or `extractor_resource_limit`, as when the limit stops Lean natively. Host disk use per attempt is therefore at most about 512 MiB besides the request, for as long as its scratch directory exists. That directory is kept when the container's removal is unconfirmed (`container_cleanup_unconfirmed`) and when the harness is killed mid-attempt. The macOS development profile still leaves its scratch directory writable with only the per-file limit; it is for trusted inputs only.

This was validated on 2026-10-12 against a real daemon (Colima, Docker 29.5.2, linux/arm64) with an image built from this recipe: `tests/test_docker_runtime.py`, `tests/test_docker_command.py` and the container checks in `tests/test_runner_remaining.py` passed. With the earlier writable `/job` bind mount and the image pinned before this change, the same probe left 70 files (84 MiB) in the host's scratch directory. Three verified references, including the largest graph (`lib_analysis_inequalities_main_pow_real_10`, a 10.5 MB extraction record returned on stdout), were checked again with metrics, graphs, heartbeats and axioms identical to their earlier records.
